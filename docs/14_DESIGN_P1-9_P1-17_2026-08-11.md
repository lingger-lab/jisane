## P1-9. refund lost-update — Toss 전 원자적 예약

### 현재 결함 (docs/11 P1-9, docs/12 §4)
`refund/route.ts`: `refunded_amt`를 **읽고**(46) 초과 검증(69) 후 Toss 취소(80) → DB 기록(90).
동시 부분환불 2건이 같은 `refunded_amt=0`을 읽으면 둘 다 상한을 통과하고, 마지막 write가
앞의 것을 덮어 **누적 환불액이 유실**된다(1만+2만 → DB엔 2만). 단순 CAS를 DB에 걸면
"Toss는 취소됐는데 DB 기록 실패"라는 더 나쁜 불일치가 생기므로(§4 확정), 순서 재설계가 필요.

### 설계: 예약(reserve) → Toss → 확정/롤백
신규 RPC 2개 (SECURITY DEFINER, service_role 전용):

```sql
-- 원자적 예약: 상한 검증과 가산을 한 문장으로. 통과 시 새 누적액 반환, 초과/경합 시 0행.
CREATE FUNCTION reserve_refund(p_settlement_id uuid, p_amount int, p_cap int)
RETURNS TABLE (new_refunded_amt int) AS $$
  UPDATE settlement
     SET refunded_amt = COALESCE(refunded_amt, 0) + p_amount
   WHERE id = p_settlement_id
     AND escrow_status IN ('deposited', 'reviewing')
     AND COALESCE(refunded_amt, 0) + p_amount <= p_cap
  RETURNING refunded_amt;
$$ LANGUAGE sql;

-- 보상 롤백: Toss 실패 시 예약분 감산 (감산 결과 음수 방지 가드 포함)
CREATE FUNCTION cancel_refund_reservation(p_settlement_id uuid, p_amount int)
RETURNS TABLE (new_refunded_amt int) AS $$
  UPDATE settlement
     SET refunded_amt = GREATEST(COALESCE(refunded_amt, 0) - p_amount, 0)
   WHERE id = p_settlement_id
  RETURNING refunded_amt;
$$ LANGUAGE sql;
```

라우트 새 순서:
1. 입력 검증(정수·사유) → settlement 조회(payment_key null이면 409 — c54a938 반영됨).
2. `reserve_refund(id, amount, totalPay)` — **0행이면 409**(초과 또는 경합 패배). 이 시점부터
   금액은 예약됨: 경쟁 요청은 정확한 누적액 기준으로 검증된다.
3. Toss 취소 (기존 멱등키 `refund_{id}_{예약후누적액}` 유지 — 예약이 직렬화하므로 누적액 유일).
4. 실패 시 `cancel_refund_reservation` 롤백 + 500. **롤백 실패는 CRITICAL 로그**(P3-98 패턴)
   — 이 경우 DB가 Toss보다 많이 기록된 상태로 남으므로 수동 정합 대상임을 명시.
5. 성공 시 `refund_reason`/`refunded_at`/전액이면 `escrow_status='refunded'` 갱신(이미 예약된
   행 대상이라 경합 없음).

잔여 리스크(정직 기록): 4의 롤백 실패 창(Toss 실패+DB 롤백 실패 동시)은 남는다 — 이는 현재
결함(무검증 lost-update)보다 좁고, CRITICAL 로그로 가시화된다. Toss 성공 후 5의 부가필드
갱신 실패는 금액 정합에는 영향 없음(예약이 이미 확정 금액).

## P1-17. 정산 release + 원장 적립 단일 트랜잭션

### 현재 결함 (docs/11 P1-17, docs/12 §4)
`auto-settlement.ts` steps 4~8이 비트랜잭션: release UPDATE(4) 후 원장 INSERT(5)가 실패하면
**console.error만 남고 released는 확정** → 적립금 원장 드리프트(정산은 나갔는데 적립 기록 없음).
audit sampling·score 재계산·owner 카운터(6~8)는 파생값이라 지연 허용 가능 — 문제는 4↔5의 금전 정합.

### 설계: release+원장을 RPC 하나로
```sql
-- 한 트랜잭션: CAS release + 원장 적립. 실제 released된 행만 적립하고 그 id를 반환.
CREATE FUNCTION release_settlements_with_ledger(p_ids uuid[])
RETURNS TABLE (released_id uuid) AS $$
BEGIN
  RETURN QUERY
  WITH released AS (
    UPDATE settlement
       SET escrow_status = 'released', released_at = now(), auto_processed = true
     WHERE id = ANY(p_ids) AND escrow_status = 'reviewing'   -- CAS 유지 (P1-16)
    RETURNING id, guarantee_fee
  ), ledger AS (
    INSERT INTO guarantee_fund_ledger (settlement_id, entry_type, amount, note)
    SELECT id, 'accrue', guarantee_fee, '자동 정산 — 책임 적립금 적립'
      FROM released WHERE guarantee_fee > 0
  )
  SELECT id FROM released;
END $$ LANGUAGE plpgsql;
```

`autoReleaseSettlements` 변경: steps 4~5를 이 RPC 1회 호출로 교체(반환 id 집합이 기존
`releasedRows` 역할). RPC 에러면 전체 중단(fail-closed, 기존 releaseError 처리와 동일).
steps 6~8(샘플링·score·카운터)은 기존대로 RPC 밖 — 실패해도 금전 정합은 깨지지 않는
파생값이므로, 기존의 loud 로그 유지. 기존 vitest mock은 `rpc()` 경유로 조정.

수동 release 경로가 있으면(관리자 UI) 동일 RPC를 재사용해 단일 소스로.
