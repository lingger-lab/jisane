## 1. 매칭 방식 — B안(기업 초빙) + AI 하이브리드

### 1.1 핵심 원칙

기존 A안(관리자/AI가 매칭 후보를 골라 전문가에게 제안)에서, **기업이 직접 전문가를 초빙**하는 B안으로 축을 이동한다. 이유는 지사네의 핵심 서사인 **"시니어 전문가 존중"** 과 일치하기 때문이다. 전문가는 자기 단가를 스스로 책정하고, 기업은 그 값어치를 인정해 "모셔간다".

### 1.2 흐름

```
[전문가] 프로필 등록 (시간당 단가 설정)
              │
              ▼
[기업] 카테고리 선택 → 전문가 리스트(≤10, 종합점수순)
              │
       [점수 + 시간당 단가] 비교
              │
       선택 피로 시 → AI가 후보 추천 (보조)
              │
              ▼
[기업] 특정 전문가 [초빙하기]
              │
              ▼
[전문가] 초빙 수신 → 의뢰 확인 → 수락/거절
```

### 1.3 AI 추천의 위치

AI는 매칭을 **지배하지 않는다**. 리스트 상단에 "이 의뢰엔 이 분들이 잘 맞아요" 추천 뱃지만 얹는 **보조 역할**이다. 주도권은 기업에게 있다.

## 2. 평가점수 모델

### 2.1 종합점수 산정식

```
종합점수 = (경력점수 × 1 + 리뷰점수 × 2 + 완료율점수 × 1) ÷ 4
```

리뷰(실제 만족도)에 2배 가중을 둔다. 완료율만 높고 리뷰가 나쁜 전문가가 과대평가되는 것을 방지한다.

### 2.2 항목별 산정

**① 경력점수 (5점) — 가입 시 확정, 관리자 검증**

| 경력 | 점수 |
|------|------|
| 30년 이상 | 5.0 |
| 20년 이상 | 4.0 |
| 10년 이상 | 3.0 |
| 5년 이상 | 2.0 |
| 5년 미만 | 1.0 |

**② 리뷰점수 (5점) — 기업 별점 + 관리자 검수**

- 리뷰 0건 → **3.0 (기본점수)**
- 리뷰 1건 이상 → 기업 별점 평균 (관리자 검수 후 반영)

**③ 완료율점수 (5점) — done/accepted 비율**

- 실적 0건 → **3.0 (기본점수)**
- 실적 1건 이상 → 완료율(%) × 5 (예: 완료율 90% → 4.5점)

### 2.3 신규 전문가 표시

```
┌────────────────────────────────────────┐
│ 김○○  [🆕 신규]     종합 3.67점        │
│ 경력 30년 ─ 5.0 | 리뷰 3.0 | 완료 3.0   │
│ (5.0×1 + 3.0×2 + 3.0×1) ÷ 4 = 3.5      │
└────────────────────────────────────────┘
```

> **중요**: 신규자의 3.0은 실적이 아니라 기본값이다. **[🆕신규] 뱃지로 반드시 명시**하여 기업이 거짓 신뢰를 갖지 않게 한다. 점수는 신뢰를 만들되, 거짓 신뢰를 만들면 플랫폼이 죽는다.

## 3. 활동지표 (밴드·게시글 가점) — 종합점수와 분리

### 3.1 분리 원칙

밴드 활동은 **전문 능력의 증거가 아니라 참여 성실성**이다. 종합점수(능력)에 섞으면 점수가 오염된다. 따라서 **별도 지표**로 두고, 정렬에서는 **동점 시 우선순위**로만 작용한다.

```
┌──────────────────────────────────────────┐
│ 김○○  [🆕신규]                          │
│ 전문점수 3.5  |  🔥활동 +2 (밴드·글 3건) │
└──────────────────────────────────────────┘
```

### 3.2 가점 규칙 (자동 계산)

| 활동 | 가점 | 처리 |
|------|------|------|
| 지사네 밴드 등록 | +1 | 링크 인증 시 자동 |
| 전문글 게시 (1건) | +0.5 | 관리자 승인 게시물만, **상한 +2** |

- 관리자는 "글 승인"만 담당, 가점 계산은 자동 (park/brad/kim 노동 최소화)

### 3.3 유효기간

- **최근 3개월 활동만 유효** (오래된 글로 상단을 독식하는 "고인물" 방지)

> **전제**: 밴드(네이버, 외부)는 초기 부트스트랩 수단이다. **종착지는 지사네 자체 게시판**이라는 전제를 유지한다. 외부 플랫폼 종속을 임시로만 허용한다.

## 4. 가격 구조 — 시간 척도 + 견적 + 캡

### 4.1 설계 논리

시간은 **가장 공평하지만 가장 위험한** 기준이다.

- **공평한 이유**: 시니어의 가치는 산출물의 양(페이지)이 아니라 판단의 밀도에 있다. 시간 기준은 "경험의 압축"을 인정한다.
- **위험한 이유**: (1) 역인센티브 — 빨리 끝내면 손해라 유능한 전문가가 불리, (2) 견적 불확실 — 기업이 총액을 몰라 결제를 못 누름.

**해법**: 시간을 *척도*로, 총액을 *약속*으로 이중화한다.

### 4.2 가격 흐름

```
[전문가] 프로필: 시간당 단가 설정
   ₩10,000 ─────●───── ₩100,000  (기준 ₩25,000)
              │
              ▼
[초빙 수락] 전문가가 예상 소요시간 산정
   "이 의뢰 → 예상 8시간"
   8h × ₩40,000 = 예상총액 ₩320,000
   캡(상한) = ₩320,000
              │
              ▼
[기업] 예상총액 확인 → [승인 & 결제] (Toss 에스크로 예치)
              │
              ▼
[정산] 캡(예상액) 고정
   → 조기 완료(6시간)해도 예상액 ₩320,000 그대로 정산
```

### 4.3 캡 정산 규칙 (확정: 예상액 고정)

- 실제 작업이 예상보다 **적게** 걸려도 **예상액 그대로 정산** (건당 계약처럼)
- 예상 시간 **초과분**은 기업 재동의 없이 과금 불가

### 4.4 예상시간 산정 위치

5단계 워크플로우의 **intake 단계**에서 예상 소요시간(`est_hours`)을 확정한다.

## 5. 품질 보증 — 신규자 첫 거래 1회 한정

### 5.1 설계 논리

이는 **신뢰 비용을 누가 선지불하는가**의 문제다. 신규 전문가와 기업 사이엔 신뢰가 없다. 기업이 위험을 지면 신규자를 안 쓴다. **지사네가 위험을 선지불**하면, 신규자는 기회를 얻고 기업은 안심한다. 신규자가 실적을 쌓으면 그 신뢰 비용을 회수하는 **투자 논리**다.

### 5.2 보증 형태 (확정: d 혼합)

```
[1차 방어] 사전 심사 (형태 c)
  신규자 결과물을 deliver 전, verify 단계에서
  관리자가 검수 통과시켜야 기업에 전달
        │
        │ 그래도 불만족 시
        ▼
[2차 방어] 환불 보증 (형태 a)
  guarantee_fund_ledger(적립금)에서 환불
```

사전 심사로 사고를 예방하고, 그래도 문제면 적립금으로 환불하는 **2중 방어**다.

### 5.3 보증 발동 조건 (필수 범위 제한)

무제한 보증은 플랫폼을 파산시키고 먹튀를 부른다. 반드시 아래로 제한한다.

- ✅ **신규 전문가(리뷰 3건 미만)의 첫 거래에 한함**
- ✅ **1회 한정** (같은 기업 반복 악용 차단)
- ✅ verify 단계까지 완료된 건에 한함
- ✅ "명백한 미이행"만 (단순 취향 불만족 제외)
- ✅ 보증 재원 = `guarantee_fund_ledger` 잔액 한도 내

> **역선택 경고**: 보증이 매력적이면 기업이 "어차피 보증되니 신규자부터 써보자"고 몰려, 검증된 전문가가 안 팔리는 역선택이 생길 수 있다. **"신규자 첫 거래 1회 한정"이라는 희소성**을 반드시 유지한다. 좋은 안전망은 촘촘하되 좁아야 한다.

## 6. 스키마 변경안

### 6.1 `partner` 테이블 — 필드 추가

```
partner
  + hourly_rate         INT      시간당 단가 (10000~100000)
  + career_years        INT      경력 연수
  + career_score        DECIMAL  경력점수 (가입 시 확정)
  + review_score        DECIMAL  리뷰점수 (기본 3.0)
  + completion_score    DECIMAL  완료율점수 (기본 3.0)
  + total_score         DECIMAL  종합점수 (가중평균 자동계산)
  + activity_points     DECIMAL  활동지표 (밴드·글, 별도)
  + is_newbie           BOOL     신규 여부 (리뷰 3건 미만)
```

### 6.2 신규 테이블 — `partner_activity`

```
partner_activity
  id, partner_id (FK)
  type         ENUM(band_join, post)
  points       DECIMAL
  approved_by  manager_name        글은 관리자 승인
  created_at   TIMESTAMP
  expires_at   TIMESTAMP           3개월 유효기간 판정
```

### 6.3 신규 테이블 — `invitation` (초빙 = B안의 새 출발점)

```
invitation
  id, client_id (FK), partner_id (FK)
  request_id (FK)              의뢰 연결 (선택적)
  status       ENUM(invited, accepted, declined)
  est_hours    INT             전문가 예상 소요시간
  est_amount   INT             예상총액 = est_hours × hourly_rate
  cap_amount   INT             캡 (= est_amount, 예상액 고정)
  created_at
```

### 6.4 기존 enum·필드 변경

```
request_status: open → matching → dealt → closed
  → 초빙이 먼저일 수 있으므로 request 없이도 거래 성립 허용
    (invitation이 request를 대체하는 경로 추가)

review 테이블 연결
  review.author = client → 별점 집계 → 관리자 검수 → partner.review_score 갱신

guarantee_fund_ledger
  + reason ENUM에 'newbie_guarantee' 추가 (신규자 보증 환불 추적)

client 테이블 (⑬ 이력 뱃지)
  + completed_deals  INT   거래 완료 건수 (점수 아님, 신뢰 신호용)
    → 시니어가 초빙 수락 전 "이 기업 거래 N건" 확인 가능

partner_interest 테이블 (⑭ 관심표현 양방향)
  → 기업 마이페이지 "받은 관심표현" + 의뢰 상세 양쪽에서 조회
  + 동시 활성 관심표현 5개 제한 (조정 가능한 설정값)

invitation 테이블 (초빙 5개 제한)
  + 시니어별 status='invited' 동시 5개 제한 (조정 가능한 설정값)
```

### 6.5 워크플로우 강화

```
5단계: intake → structure → generate → verify → deliver

   (est_hours 확정)             (관리자 검수 게이트)

```

## 7. 화면 흐름 설계

### 7.1 기업(Owner) 화면 — 6단계

```
① 랜딩 /              → 소개·통계·카테고리, [의뢰하기]
② 의뢰 작성 /request  → 카테고리 3레벨·상세·예산, request(open)
③ 현황 /status·[id]   → 매칭 후보·견적·메시지, [견적 승인]
                        ★ 전문가 리스트에 "✓품질인증" 뱃지 표시(점검2)
④ 결제 (Toss)         → 에스크로 예치, settlement(deposited)
⑤ 진행 확인           → 5단계 워크플로우 관전
⑥ 완료 & 정산         → [완료 확인], settlement(released), 리뷰 작성
```

기업의 3대 핵심 결정: **① 뭘 맡길까(의뢰) ② 누구에게·얼마에(승인) ③ 됐다고 할까(완료 확인)**. 나머지 화면은 이 3개 결정을 돕는 장치다.

### 7.2 기업 마이페이지 `/mypage`

```
【기본 프로필】 담당자명·회사명·연락처·이메일·사업자정보·로그인연동
【내 의뢰 이력】 open / matching / dealt / closed (request 생애주기 전체)
【내가 초빙한 이력】 invited / accepted / declined (invitation, 기업 관점)
【받은 관심표현】 내 의뢰에 관심 보인 전문가 목록 ← 관심표현 양방향(⑭)
【결제·정산 이력】 deposited / released / refunded(신규자 보증 포함)·누적결제액
【주문 내역】 AX/비즈 컨설팅 패키지 (service_order)
【내가 쓴 리뷰】 완료 거래 별점·리뷰 (author: client)
【이력 뱃지】 "거래 완료 N건" — 기업 신뢰 신호(⑬), 점수 아님
【계정·설정】 알림·탈퇴
```

### 7.3 시니어 전문가(Partner) 화면 — 8.5단계

```
① 랜딩 /              → "수수료 0%"·시니어 존중, [전문가 등록]
② 프로필 등록 /register → 분야·경력·시간당단가·자기소개
                          ★ 관리자 "품질 인증"(심사 아님, 자존심 보호)
                          partner(waiting → 인증후 active)
③ 활동 가점 쌓기       → 밴드 등록·전문글, 활동지표 🔥 (계속 노출)
③.5 공개 의뢰 탐색 /requests → [보조 경로] 전체 의뢰 열람
                          관심 표현(♡) — 동시 5개 제한
                          partner_interest 생성
④ 초빙 수신 /matching  → [기본 경로] 나를 초빙한 것, 대기 5개 제한
                          ★ 초빙한 기업의 "거래 N건" 뱃지 표시(⑬)
                          [수락]→invitation(accepted) / [거절]→declined
⑤ 예상시간 산정        → intake, est_hours×단가=예상총액, 캡 고정
⑥ 작업 수행 /work      → 5단계 워크플로우
⑦ 완료 & 정산 수령     → released·정산금(=cap)·리뷰 수신
⑧ 마이페이지 /mypage   → (아래 7.4)
```

**두 매칭 경로** (⑬ 확정: 기업 초빙이 기본):
```
경로1 (기본):  기업이 초빙 → 시니어 수락
경로2 (보조):  시니어가 공개의뢰에 관심표현 → 기업이 초빙
```

### 7.4 시니어 마이페이지 `/mypage`

```
【기본 프로필】 이름·연락처·이메일·사진·분야·소개·시간당단가[수정가능]
【점수·등급】 종합점수(경력·리뷰·완료율 분해)·등급·활동지표🔥(계속노출)
【나를 초빙한 이력】 invited / accepted / declined (invitation, 시니어 관점)
【관심 표현 이력】 내가 관심표현한 공개의뢰(5개 중 N개)·초빙 전환 여부
【거래·정산】 작업이력·누적정산액·받은 리뷰
【의뢰 필터】 내 카테고리 맞춤 공개의뢰 (③.5 전체 탐색과 별개 화면)
             → 탐색 공간(③.5)과 내 관리 공간(마이페이지)을 분리해 목적 명확화
【계정·설정】 로그인연동·알림·탈퇴
```

### 7.5 기업 ↔ 시니어 대칭 구조

| 축 | 기업(고르는 자) | 시니어(골라지는 자) |
|----|----------------|-------------------|
| 기본정보 | 회사·담당자·사업자 | 개인·경력·자기소개 |
| 평판 | **이력 뱃지만**(거래 N건, ⑬) | 종합점수·등급·활동지표 |
| 능동 활동 | 내가 초빙한 이력 | 내가 관심표현한 이력 |
| 수동 활동 | 받은 관심표현(⑭) | 나를 초빙한 이력 |
| 돈 | 결제·정산·환불 이력 | 정산 수령·누적액 |
| 리뷰 | 내가 쓴 리뷰 | 받은 리뷰 |

> **설계 원리**: 생애주기(invited→accepted→declined 등)를 가진 모든 객체는 **"현재 처리하는 액션 뷰"**(예: ④ 초빙 수신)와 **"전체를 조회하는 이력 뷰"**(마이페이지)가 한 쌍으로 필요하다. 초빙·관심표현·정산 모두 이 원리를 따른다.

### 7.6 과잉 접근 방지 (양방향 매칭의 안전장치)

```
관심표현 5개 제한   → 시니어가 동시 활성 관심표현 최대 5개
초빙 수신 5개 제한   → 시니어별 status=invited 동시 최대 5개
                      (6번째 초빙 시 기업에게 "초빙 마감" 표시)
```

- **의미**: 단순 스팸 방지가 아니라 "비용 있는 신호(costly signaling)". 제한이 곧 진정성의 증거.
- **개발 주의**: 5는 검증 안 된 출발값. **하드코딩 금지, 조정 가능한 설정값으로** 구현 (초기엔 과다·성장 후엔 과소일 수 있음).

## 8. 관리자 화면 설계 (사람 관여 최소화)

### 8.1 설계 원칙 — "관리자가 안 봐도 되게 만드는 창"

일반 대시보드는 "관리자가 모든 걸 보는 창"이지만, 지사네 관리자 화면의 목표는 **"관리자가 안 봐도 되게 만드는 것"**이다. 자동화가 완벽해질수록 화면은 비어간다. 성공 지표는 정보량이 아니라 **상단 "🔴🟡 카운터가 얼마나 자주 0인가"** 이다.

### 8.2 업무 자동화 등급 (11개 업무)

```
🟢 자동   : 규칙 충족 시 자동 처리, 사람 개입 0
🟡 반자동 : 자동 1차 필터 → 애매/경계선만 사람 큐잉
🔴 수동   : 반드시 사람 판단 (드물지만 중요)
```

| 업무 | 등급 | 자동화 규칙 | 사람이 보는 것 |
|------|------|------------|---------------|
| 매칭 모니터링 | 🟢 | 정상 흐름 자동 | 막힌 것만 |
| 정산 release | 🟢 | 완료확인+캡일치+분쟁없음 | 조건 미충족만 |
| 정산 refund | 🔴 | 돈 나가는 일 | 전건 |
| 전문글 승인 | 🟡 | 금칙어·표절 통과 | 경계선만 |
| 리뷰 검수 | 🟡 | 텍스트 정상+신고없음 | 신고된 것만 |
| 품질 인증 | 🟡 | 경력서류 체크리스트 | 애매한 것만 |
| 신규자 보증심사 | 🔴 | 돈·신뢰 예외 | 전건 |
| 보증 환불결정 | 🔴 | 먹튀 판정 | 전건 |
| 관심표현 라우팅 | 🟢 | 시니어→기업 자동 알림 | 개입 불필요 |
| 문의 1차 | 🟡 | 챗봇 자동응답 | human_routed만 |
| 서비스 주문 | 🟢 | 결제완료 자동전이 | 취소·환불만 |

→ **🟢 5개는 화면에서 사라지고(로그만), 🟡 4개는 예외 큐만, 🔴 3개는 전건이나 드묾**

### 8.3 대시보드 구조 (4그룹)

```
┌─ 상단: "사람 손이 필요한 것" 카운터 ──────────────────┐
│  🔴 즉시처리 N (환불·보증)  🟡 검토대기 N (인증·검수·문의) │
│  → 0이면 관리자는 대시보드를 열 필요도 없음              │
└─────────────────────────────────────────────────────────┘

그룹 A. 거래 흐름     [매칭]🟢 [진행]🟢 [정산]🟢release/🔴refund
그룹 B. 신뢰 관리     [인증]🟡 [검수]🟡 [승인]🟡  ← 예외 큐만
그룹 C. 분쟁·보증     [보증심사]🔴 [환불결정]🔴 [적립금]🟢
그룹 D. 지원         [문의]🟡 [서비스]🟢 [관심표현 라우팅]🟢
```

관리자 하루 동선: 아침에 상단 카운터 확인 → 🔴 즉시처리 → 🟡 큐 → 나머지는 자동.

### 8.4 자동화 판정 로직 (개발 전달용)

```
[품질 인증] IF 경력증빙 AND 카테고리-경력 일치 AND 금칙어 없음 → 자동 ✓뱃지 / ELSE 큐
[리뷰 검수] IF 별점 정상 AND 금칙어 없음 AND 신고이력 없음 → 자동 반영 / ELSE 큐
[전문글 승인] IF 표절통과 AND 금칙어 없음 AND 최소글자수 → 자동 +0.5 / ELSE 큐
[정산 release] IF 완료확인 AND 정산액=cap AND 분쟁없음 → 자동 release / ELSE 🔴확인
```

### 8.5 사후 감사 장치 (자동화 안전망) ★

자동화의 숨은 위험 — "자동 통과분에 문제가 섞이면 아무도 못 잡는다" — 를 막는 2중 그물. 앞단에서 뺀 사람 관여를 뒷단에 최소한으로 남긴다.

```
안전망 1: 무작위 샘플 감사 (능동)
  🟢🟡 자동 처리분의 5%를 무작위 추출 → 관리자 재검토 큐
  → 자동화 로직이 조용히 틀리는지 조기 발견 → 규칙 보정

안전망 2: 사용자 이의제기 (수동)
  시니어 "이 리뷰 부당" → 자동반영 리뷰 재심 큐
  기업 "결과물 문제" → 자동정산 전이면 보류·재검토
  → 자동화가 놓친 것을 당사자가 사후에 잡음
```

> **철학**: "완전 자동화"가 아니라 **"자동화 + 사후 그물"**. 사람 관여를 앞단(전건 검토)에서 빼되, 뒷단(샘플 감사·이의제기)에 얇게 남긴다.

### 8.6 관리자 화면 스키마 추가

```
공통 (🟡🟢 업무 테이블)
  + auto_processed  BOOL     자동 처리 여부
  + queue_status    ENUM(auto_passed, pending_review, audited)
  + audit_sampled   BOOL     무작위 감사 대상 추출 여부(5%)

이의제기
  dispute
    id, target_type ENUM(review, settlement), target_id
    raised_by ENUM(client, partner)
    reason TEXT, status ENUM(open, resolved)

🔴 수동 3건 (refund·보증심사·환불결정)
  → manager_name 담당 지정 필드 열어둠 (지정 방식은 추후 결정)
```

## 9. 전문서비스 마켓플레이스 (제공기관 2단 구조)

### 9.1 문제 — 산발적 서비스 나열

현재 기업공간("140+ 전문 서비스를 둘러보세요")과 시니어공간("당신의 30년, AI로 증폭하다")은 서비스를 **평면 나열**한다. "140+"라 하면서 화면엔 6개만 뜨고, 제공기관(현재 전부 엔터랩스)이 드러나지 않는다. 향후 변리사·변호사·세무사·회계·손해사정 업체가 입점하면 감당 불가.

### 9.2 재설계 — 제공기관 → 서비스 2단

```
[변경 전] 서비스 직접 나열
   AX무료진단 / AX전환코칭 / AI사업진단 ...

[변경 후] 제공기관 카드 → 클릭 → 그 기관의 서비스
   ┌─────────────────────────┐
   │ 🏢 엔터랩스              │  ← 기관 카드(최소: 기관명·서비스수)
   │ 서비스 12개             │
   │         [서비스 보기 →] │
   └─────────────────────────┘
   ┌─────────────────────────┐
   │ ⚖️ ○○특허법률 (변리사)  │  ← 향후 입점
   │ 서비스 5개              │
   └─────────────────────────┘
        │ 클릭
        ▼
   엔터랩스 서비스 목록 (기존 6개 카드가 여기로)
```

랜딩엔 기관 카드만 깔끔히, 서비스 상세는 한 단계 안으로. "140+"는 기관 카드에 "서비스 N개"로 집계.

### 9.3 두 경로 완전 별개 (판단 A)

전문서비스는 기존 "전문가 직접 초빙"과 **완전히 별개 경로**다.

| | 전문가 직접 초빙 | 패키지 서비스 구매 |
|---|----------------|-------------------|
| 파는 것 | **사람**(시니어 개인) | **서비스**(기관 패키지) |
| 신뢰 방식 | 점수·인증·에스크로·신규자보증 | 기관 단위 |
| 구조 | invitation·5단계 워크플로우 | service_order |

> **정체성 원칙**: "사람 직거래"와 "기관 서비스"를 명확히 분리한다. 지사네의 핵심 서사(시니어 개인 존중 직거래)를 지키면서, 전문서비스는 별도 마켓플레이스로 확장한다.

### 9.4 무료/유료 이중 구조 (성장 엔진)

전문서비스는 단순 판매가 아니라 **플랫폼 성장 깔때기**다.

```
[무료 서비스] = 가입 전환 장치 (미끼 아닌 gateway)
  예: AX 무료진단
  · 기업: 부담 없이 첫 경험 → 가입 유인
  · 시니어: 무료 교육 맛보기 → 등록 유인
  · 플랫폼: 트래픽·신뢰 확보
       │
       ▼ (무료로 맛본 뒤 자연 전환)
[유료 서비스] = 제공업체의 수익 기회
  예: AX전환코칭, 특허출원(변리사), 세무대행(세무사)
  · 플랫폼: 입점 업체에게 "기회를 주는" 마켓플레이스
```

무료 서비스는 손해가 아니라 **전환 장치**. 무료/유료는 서비스 카드에 **명확히 구분 표시**한다.

### 9.5 컴포넌트·스키마

```
공용 컴포넌트 (기업·시니어 재사용, 카피·데이터만 분리)
  <ProviderCard>         기관명·로고·서비스수·링크 (최소, 판단 B)
  <ProviderServiceList>  기관 클릭 후 서비스 목록 (무료/유료 구분)

신규 테이블
  provider (제공기관)
    id, name, logo
    type ENUM(consulting, legal, tax, accounting, insurance)
    → 현재 엔터랩스 1개 row, 입점 시 row 추가만

service 테이블 변경
  + provider_id  FK        서비스를 기관에 연결 (현재 전부 엔터랩스)
  + is_free      BOOL      무료/유료 구분 (가입 전환 장치)
```

`provider` 테이블이 핵심 — 지금은 엔터랩스 1개뿐이지만, 외부업체는 row 추가만으로 입점. **서비스를 기관에 매다는 구조**라 확장이 자연스럽다.

### 9.6 기존 홈페이지에서 유지할 패턴

owner.jisane.cloud의 잘 된 부분은 유지: "이런 경험 있으셨나요?"(공감→문제), "감추는 관행 vs 지사네"(신뢰 대비 테이블), 카테고리 그리드(이미 2단 구조). **전문서비스도 카테고리 그리드와 같은 시각 언어**로 만들어 페이지 일관성 확보.

### 9.7 전략적 의미

이 재설계는 UI 정리가 아니라 **엔터랩스의 포지션 전환**이다 — "서비스를 파는 회사"에서 "제공자들을 모으는 플랫폼"으로. 제공기관 층을 만드는 순간, 여러 공급자가 입점하는 그릇이 생긴다.

## 10. 미해결·검증 필요 사항

설계는 완결됐으나, **설계로 답할 수 없는 가정**이 하나 남아 있다.

> **검증 필요 (최우선)**: B안의 핵심 전제는 "기업이 스스로 전문가를 고를 것"이다. AI를 모르는 사장님이 실제로 10명의 점수·단가를 비교하며 고를지, 아니면 결국 "그냥 알아서 매칭해줘"(A안)로 돌아갈지는 **실제 사용자 2~3명에게 물어봐야** 안다. 다음 단계로 넘어가기 전 이 전제를 검증할 것을 권장한다.
